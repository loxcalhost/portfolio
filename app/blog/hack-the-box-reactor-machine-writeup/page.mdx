## Introduction

Reactor is a Linux-based machine that highlights the risks of running outdated web frameworks and leaving development debugging tools exposed in a production environment. The exploitation path requires a solid understanding of modern web application vulnerabilities, local enumeration, and process architecture. This writeup details the steps to compromise the machine, moving from a publicly accessible web application to full root access.

## Overview

The compromise begins by targeting a Next.js web application running on port 3000. The application is running version 15.0.3, which is vulnerable to CVE-2025-55182 (React2Shell). Exploiting this Server-Side Remote Code Execution vulnerability yields an initial shell.

Post-exploitation enumeration reveals a local SQLite database containing MD5 password hashes. Cracking these hashes offline provides the password for the `engineer` user, allowing for lateral movement via SSH. Finally, privilege escalation is achieved by discovering a local Node.js process running as root with the V8 Inspector debugging interface enabled. By port-forwarding the debug port and interacting with it via the Chrome DevTools Protocol, arbitrary JavaScript is executed to set the SUID bit on `/bin/bash`, resulting in a root shell.

## Attack Chain

- **Initial Access:** Exploiting CVE-2025-55182 (React2Shell) on a Next.js web application.
- **Credential Harvesting:** Locating a local SQLite database (`reactor.db`) and extracting MD5 user hashes.
- **Offline Cracking:** Using Hashcat to crack the `engineer` user's hash.
- **Lateral Movement:** Logging in as `engineer` via SSH using the cracked credentials.
- **Local Enumeration:** Identifying an exposed Node.js debugger on internal port `9229`.
- **Privilege Escalation:** Tunneling the debug port and executing arbitrary code via the V8 engine to obtain root privileges.

## Foothold

The root cause of **CVE-2025-55182** is that React Server Components rely on a custom Flight protocol to serialize and transmit component data between the server and client.

React decodes incoming RSC payloads using a deserialization mechanism that reconstructs component definitions, references, and function calls.

The vulnerability primarily arises because:
- React trusts client-supplied RSC payloads
- It performs insufficient type and object validation
- It reconstructs objects in a way that enables arbitrary function invocation

As a result, an attacker can craft malicious RSC payloads that reference internal React server functions, leading to arbitrary JavaScript execution on the server.

Even if a web application does not explicitly use server functions, it may still be affected because the vulnerable code is included by default when React Server Components packages are installed.

The exploitation process begins by identifying React Server Component routes. The attacker then sends a request containing a malicious RSC payload designed to instantiate server-side functions. React attempts to reconstruct this payload into a valid RSC message, and during deserialization it interprets `$f` values as function references.

It then resolves object references without verifying the legitimacy of their source and passes the reconstructed data directly into the server’s execution context. This ultimately causes React to invoke a server function, resulting in server-side command execution rather than merely client-side JavaScript evaluation.

The process output indicates that `worker.js` is running as **root**, and it was started with the `--inspect` flag. This enables the Node.js V8 Inspector, which is intended for debugging in development environments, not production.

The inspector exposes a debugging interface that allows anyone who can connect to it to evaluate and execute arbitrary JavaScript code within the context of the running application.

We inspected the source code of `/opt/uptime-monitor/worker.js` to see if there were any code-level vulnerabilities, such as command injection. The code is a simple loop that makes HTTP requests to a local service and safely writes the metrics to a CSV file.

Because the code itself is secure, we must rely entirely on the environmental misconfiguration: the `--inspect` flag used to launch the process. Because the process is wrapped in the Node debugger, we can bypass the secure script entirely and feed arbitrary commands directly to the underlying Node.js engine running as root.

Since Node.js is running on the V8 engine, a Chromium-based browser is required to access its debugging interface.

The `--inspect` flag enables the V8 Inspector, which starts a debugging server that listens for Chrome DevTools Protocol (CDP) messages.

CDP (Chrome DevTools Protocol) is the official interface used to inspect, debug, and profile Chromium-based browsers and the V8 JavaScript engine.

To access it, open a Chromium-based browser and navigate to:

```
chrome://inspect
```

In the page, ensure that **"Discover network targets"** is enabled.

Click **Configure** and add the target:

```
localhost:9229
```

Then click **Done**.

Under **Remote Target**, the running script `/opt/uptime-monitor/worker.js` will appear.

Click **Inspect** to open the DevTools window and access the console.

In the console, run the following code:

```
const { exec } = require('child_process');

exec('chmod u+s /bin/bash', (err, stdout, stderr) => {
  if (err) {
    console.error(err);
    return;
  }
  console.log('SUID bit set successfully');

```

## Remediation & Recommendations

1. **Patch Web Frameworks (CVE-2025-55182):** The Next.js framework must be updated to a patched version immediately to prevent unauthenticated Remote Code Execution. Ensure that all dependencies, especially those handling React Server Components, are regularly audited and updated.
2. **Secure Credential Storage:** The SQLite database stores user passwords using MD5, which is a weak and deprecated hashing algorithm. Passwords should be hashed using modern, computationally expensive algorithms such as Argon2, bcrypt, or scrypt. Additionally, enforce strict password complexity requirements to prevent offline dictionary attacks (e.g., `reactor1` is highly insecure).
3. **Disable Debugging Interfaces in Production:** The `/opt/uptime-monitor/worker.js` script was launched with the `--inspect` flag. Debugging interfaces must never be enabled in production environments, as they bypass application logic and allow for arbitrary code execution. Remove the `--inspect` flag from the startup script or service file.
4. **Principle of Least Privilege:** The Node.js worker script was running as the `root` user. Applications and background services should always execute under a dedicated service account with the minimum permissions required to function. If the Node process had been running as a low-privileged user, the exposed debugger would not have led to full system compromise.
